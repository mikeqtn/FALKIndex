# FALK Index — MVP Plan (website + database)

**Source:** `docs/FALK_Index_v0.2_Redesigned.pdf` (Methodology Handbook v0.2, Oct 2026)
**Status:** Draft, awaiting approval. No code written yet.
**Complexity:** Medium for engineering, **High for editorial work** (evidence collection is the long pole).

---

## 1. What we're building

A public, evidence-first reference site where every watch **record** (an exact model, reference, generation, or production route) shows:

1. its **FALK Profile**: seven dimensions (MA, MM, EX, DH, CF, WE, PD), each scored 0–5 or **U**, and **never summed**
2. its **classification** (a production archetype, assigned last)
3. its **evidence confidence** (A–D)
4. the **provenance and evidence underneath each dimension**: claims, sources, excerpts, dates checked, and the editor's rationale
5. its **history**: every change carries a source, a rationale, an editor, and a date

The MVP is **read-only for the public**, with editor-controlled writes and a public **correction form**. Community editing comes after the MVP (handbook §9 describes it as the long-term goal, not something needed on day one).

### Non-goals (MVP)
- No aggregate score, leaderboard, or "sort by total". This is a hard product rule (handbook p.1, §3).
- No public accounts or wiki-style editing.
- No product photography (copyright risk; see §8).
- No paid placement of any kind (§9 "Commercial independence").

## 2. Findings from the handbook (proposed improvements)

These came up while reading the handbook. Each item affects the data model, so it should be settled before seeding.

| # | Finding | Proposal |
|---|---|---|
| F1 | **Classification vocabulary drift.** §5 defines **9** classifications, but the 56-record dataset uses **31 distinct labels** (e.g. "Integrated Haute Manufacture", "Microbrand with Internal Assembly", "Technical Atelier / Supplier Hybrid", "Industrial / In-group Supplier Model"). | Use a controlled vocabulary of the 9 archetypes. Move what the labels encode into structured fields: **ownership** (independent/group), **scale**, the **Independent Watchmaker** descriptor, and the network/in-group nature (derived from provenance relationships). See the mapping in Appendix A. |
| F2 | **"Haute" is a prestige term.** "Integrated *Haute* Manufacture" (Lange, VC, AP) conflicts with the core principle "provenance, not prestige". | Drop it. Those records become *Integrated Manufacture* with a scale/ownership tag. |
| F3 | **Inconsistent record.** J.N. Shapiro Resurgence is "Integrated Independent Manufacture / Independent Watchmaker" on p.9 but "Integrated Independent Manufacture" on p.11. Roger W. Smith has the same 5/5/5/5/5/5/5 profile but the label "Integrated Independent Watchmaker". | Make **Independent Watchmaker** a boolean descriptor, separate from the archetype, as §5 already says ("not automatically generated by thresholds"). |
| F4 | **"Designer-led Établisseur"** (Kurono) vs **"Design-led Établisseur"**. | Typo. Normalized by F1. |
| F5 | **No U appears anywhere in 56 records**, despite rule 2 ("Unknown is not zero"). | Store U as `NULL`, kept distinct from 0 in both the schema and the UI. On seed import, editors review every 0 on B/C-confidence records to decide whether it is really a 0 or a U. |
| F6 | **Confidence without a public trail.** "A" means "strong primary evidence for essentially every scored dimension", but §10 admits sources aren't yet row-level. | Import the seed data as `is_seed = true` and show it as **"Provisional: evidence pending"** until claims are attached. Confidence is re-confirmed during evidence entry. |
| F7 | **Confidence D** means "avoid a definitive profile". | Enforce this in the UI: D records show provenance notes only, with no profile strip and no classification. |
| F8 | **Rationale per dimension** is required (§6 step 4, §9) but absent from the dataset. | `profile_score.rationale` is required for any published non-seed profile. |
| F9 | **In-group scoring is undefined.** In-group suppliers must be "disclosed" (rule 7), but the handbook doesn't say whether in-group work counts toward internal scores (e.g. Tudor/Kenissi, Longines/Swatch Group). | Record `relationship` on every provenance entry so either rule can be applied and shown. This needs a methodology decision (Q7). |
| F10 | **The provenance fields map 1:1 onto the dimensions.** The seven provenance areas (§4) are exactly MA/MM/EX/DH/CF/WE/PD. | Key provenance entries by `dimension_code`. One taxonomy instead of two. |
| F11 | **Quartz and Spring Drive** (Grand Seiko 9F, 9R) are scored on MM/WE descriptors written for mechanical escapements ("or equivalent depth"). | Add a methodology note for v0.3 (Q8). Doesn't block the MVP. |
| F12 | **Methodology will change** (§9: "methodology changes require a version bump"). | Every profile stores `methodology_code`. Dimension and level text is stored per version, so old profiles are never silently reinterpreted. |
| F13 | **Open data is cheap and on-mission.** | Publish JSON/CSV exports of the full dataset in the MVP (Q5 covers the licence). |
| F14 | **Supplier pages come almost for free.** With organizations modelled, "where does Kenissi / Sellita / Miyota appear?" is just a query. | Build in Phase 4. High editorial value, low cost. |

## 3. Architecture recommendation

**Recommended: a git-backed content database plus a static site.**

| Concern | How it's met |
|---|---|
| "Version control", "Preserve the audit trail" | Git *is* the audit trail: every change has an author, a date, a diff, and a message. PR review is the editorial gate. |
| "Facts ≠ judgments", references | Records are YAML files validated against a schema (Zod), plus a cross-reference check in CI. |
| Querying / filtering | 56 records (even 5,000) are filtered client-side from one JSON file. No search server needed. |
| Hosting | Static site on Cloudflare Pages, Netlify, or GitHub Pages. No server, no database to run, no admin auth to secure. |
| Corrections | A public form that creates a moderation item (Q4). Accepted corrections become PRs. |

- **Stack:** Astro (static output, with typed content collections and Zod built in) plus TypeScript. Plain CSS is enough; no UI framework is needed for the MVP.
- **Ceiling:** non-technical editors or high-volume community edits. **Upgrade path:** first add a git-based CMS (Decap/Sveltia) on the same files. Only if real-time community editing is needed, load the same schema into Postgres. The data model below is relational for exactly this reason: the YAML mirrors it table-for-table.

The alternative (Q1) is Postgres (e.g. Supabase) with an admin UI from day one. It's faster for non-technical editors, but we would have to build auth, roles, an audit log, and backups, all of which git already provides.

## 4. Data model

The model is relational, so it ports to Postgres unchanged. In the MVP, each table is either a YAML collection or a nested list inside a watch file (see §4.3).

### 4.1 Tables

```sql
-- ── Methodology (the handbook, versioned) ─────────────────────────────
methodology_version (
  code            text PRIMARY KEY,          -- 'v0.2'
  published_on    date NOT NULL,
  notes           text
)

dimension (
  methodology_code text REFERENCES methodology_version,
  code            text CHECK (code IN ('MA','MM','EX','DH','CF','WE','PD')),
  name            text NOT NULL,             -- 'Movement Architecture'
  question        text NOT NULL,             -- 'Who is responsible for…?'
  sort            smallint NOT NULL,
  levels          jsonb NOT NULL,            -- {"0": "Stock third-party caliber", …, "5": …}
  PRIMARY KEY (methodology_code, code)
)

classification (
  methodology_code text REFERENCES methodology_version,
  code            text,                      -- 'design_led_etablisseur'
  name            text NOT NULL,             -- 'Design-led Établisseur'
  definition      text NOT NULL,
  kind            text CHECK (kind IN ('archetype','descriptor')),  -- Independent Watchmaker = descriptor
  PRIMARY KEY (methodology_code, code)
)

-- ── Who (brands, suppliers, groups, ateliers, individuals) ─────────────
organization (
  id              text PRIMARY KEY,          -- slug: 'kenissi'
  name            text NOT NULL,
  kind            text CHECK (kind IN ('brand','supplier','group','atelier','individual')),
  parent_id       text REFERENCES organization,   -- group ownership → derives "in-group"
  ownership       text CHECK (ownership IN ('independent','group','unknown')),
  scale           text CHECK (scale IN ('individual','small','medium','industrial','unknown')),
  country         text,
  website         text,
  notes           text
)

-- ── The unit of classification: model / reference / generation / route ─
watch (
  id              text PRIMARY KEY,          -- 'jn-shapiro/resurgence'
  brand_id        text NOT NULL REFERENCES organization,
  model           text NOT NULL,             -- 'Black Bay 58'
  reference       text,                      -- '79030N'
  generation      text,
  caliber         text,                      -- 'MT5402'
  route_label     text,                      -- 'Miyota-based lines', 'Shinshu'
  production_start smallint,                 -- year
  production_end   smallint,                 -- NULL = current
  notes           text
)

-- ── Facts layer ────────────────────────────────────────────────────────
source (
  id              text PRIMARY KEY,
  url             text NOT NULL,
  archived_url    text,                      -- Wayback snapshot; brand pages move
  title           text,
  publisher_id    text REFERENCES organization,
  source_type     text CHECK (source_type IN (
                    'manufacturer','workshop','supplier_disclosure',
                    'technical_interview','specialist_reference','press','other')),
  tier            text CHECK (tier IN ('primary','secondary')),  -- §9 source hierarchy
  published_on    date
)

claim (
  id              text PRIMARY KEY,
  watch_id        text REFERENCES watch,     -- one of watch_id / organization_id set
  organization_id text REFERENCES organization,
  statement       text NOT NULL,             -- the factual claim, in our words
  excerpt         text,                      -- short supporting quotation
  source_id       text NOT NULL REFERENCES source,
  dimensions      text[] NOT NULL,           -- e.g. {MA,MM,PD}
  date_checked    date NOT NULL,
  editor          text NOT NULL,
  status          text CHECK (status IN ('active','disputed','superseded')),
  superseded_by   text REFERENCES claim
)

provenance_entry (
  id              text PRIMARY KEY,
  watch_id        text NOT NULL REFERENCES watch,
  dimension_code  text NOT NULL,             -- area = dimension (F10)
  component       text NOT NULL,             -- 'hairspring', 'case', 'guilloché', 'regulation'
  performer_id    text REFERENCES organization,   -- NULL = unknown
  relationship    text CHECK (relationship IN (
                    'internal','in_group','external_specialist','contract','unknown')),
  valid_from      smallint,
  valid_to        smallint,
  note            text,
  claim_ids       text[]                     -- evidence for this entry
)

-- ── Judgment layer (append-only versions) ──────────────────────────────
profile (
  id              text PRIMARY KEY,
  watch_id        text NOT NULL REFERENCES watch,
  version         smallint NOT NULL,
  methodology_code text NOT NULL REFERENCES methodology_version,
  confidence      char(1) CHECK (confidence IN ('A','B','C','D')),
  independent_watchmaker boolean NOT NULL DEFAULT false,   -- descriptor (F3)
  status          text CHECK (status IN ('draft','published','superseded')),
  is_seed         boolean NOT NULL DEFAULT false,          -- F6
  editor          text NOT NULL,
  change_note     text NOT NULL,
  created_on      date NOT NULL,
  UNIQUE (watch_id, version)
)

profile_score (
  profile_id      text REFERENCES profile,
  dimension_code  text,
  value           smallint CHECK (value BETWEEN 0 AND 5),  -- NULL = U
  rationale       text,
  PRIMARY KEY (profile_id, dimension_code)
)

profile_classification (
  profile_id      text REFERENCES profile,
  classification_code text,
  rank            smallint NOT NULL,         -- 1 = primary; 2 = secondary for genuine hybrids
  PRIMARY KEY (profile_id, classification_code)
)

score_evidence (
  profile_id      text,
  dimension_code  text,
  claim_id        text REFERENCES claim,
  stance          text CHECK (stance IN ('supports','contradicts','context')),  -- visible disputes
  editor_note     text NOT NULL,             -- "why this evidence supports the score"
  PRIMARY KEY (profile_id, dimension_code, claim_id)
)

-- ── Public input ───────────────────────────────────────────────────────
correction (
  id              text PRIMARY KEY,
  watch_id        text REFERENCES watch,
  submitter_name  text,
  submitter_email text,                      -- private, never published
  submitter_role  text CHECK (submitter_role IN ('brand','watchmaker','reader','other')),
  body            text NOT NULL,
  source_urls     text[],
  status          text CHECK (status IN ('new','reviewing','accepted','rejected')),
  resolution_note text,
  created_at      timestamptz NOT NULL
)
```

### 4.2 Invariants (enforced by CI validation)

1. **No sums.** No aggregate field exists, and nothing in the codebase computes one.
2. **U ≠ 0.** `value` is nullable, and the UI renders U distinctly (hatched, labelled "Unknown").
3. **All seven dimensions are present** on every profile, with one `profile_score` row each, even when the value is U.
4. **Published, non-seed profiles** require a `rationale` and at least one `supports` claim for every non-U dimension.
5. **Confidence D** → at render time, no profile strip and no classification (F7).
6. **Classification codes** must exist in the profile's `methodology_code` vocabulary, with exactly one `rank = 1` archetype.
7. **A new profile version** requires a `change_note` and must bump `version`. Older versions become `superseded`, never deleted.
8. **Claims are facts, profiles are judgments.** A claim never carries a score, and a score never carries a URL directly.
9. **Disputed claims** stay visible, with their stance shown. They are never silently removed.
10. **`relationship = in_group`** should match the organization graph (performer and brand share a `parent_id` ancestor). A mismatch produces a warning.

### 4.3 MVP file layout (git-backed)

```
data/
  methodology/v0.2.yaml          # dimensions + levels + classifications
  organizations/*.yaml           # one file per brand / supplier / group
  sources.yaml                   # shared bibliography
  watches/<brand>/<model>.yaml   # watch + provenance + claims + profile versions
  corrections/                   # (only if Q4 = git-based)
```

One file per watch keeps everything an editor touches in a single PR. The current profile is the highest published `version`.

## 5. Website (MVP pages)

| Page | Content |
|---|---|
| **Home** | What FALK is, the "provenance, not prestige" principle, "not a ranking" stated up front, and the AI transparency note (p.1). |
| **Methodology** | Rendered from `methodology/v0.2.yaml`, the single source of truth for dimension and level text. Includes the foundational rules, classifications, and confidence scale, plus a methodology changelog. |
| **Index** | A table of all records with filters for brand, classification, confidence, ownership, scale, and per-dimension range (e.g. "MA ≥ 4 and MM ≤ 1", which surfaces the Fleming/Czapek-type edge cases). Sorting is by brand/model/date only. A 7-cell profile strip per row. |
| **Watch record** | Header (brand, model, ref, production years), profile strip, classification, Independent Watchmaker badge, confidence, and a seed/provisional banner. **Each dimension expands** to show its level descriptor, rationale, supporting/contradicting claims with excerpt, source tier label, date checked, and editor. Also: provenance table by area, version history with change notes, a "Suggest a correction" link, and a link to the JSON for this record. |
| **Brand** | Summary plus a list of its records. It never shows a brand-level score (rule 1: "model first"). |
| **Sources** | The bibliography with tier labels, and which records cite each source. |
| **Corrections** | The form: role, record, claim, source URLs. Shows the policy for evidence-based corrections. |
| **About** | Editorial independence, no paid placement, AI disclosure, contact, data licence. |
| **Data** | Download the full dataset as JSON/CSV (F13). |

Accessibility: the profile strip must show numbers and letters as text, not colour alone, and have a proper table fallback.

## 6. Phases

### Phase 0: Decisions (blocking, no code)
- Resolve open questions Q1–Q7 (§7). At minimum: the storage approach, the classification vocabulary, and the in-group rule.
- Confirm the Appendix A mapping with the methodology owner.
- **Exit:** decisions recorded in `docs/DECISIONS.md`.

### Phase 1: Schema + seed data
1. Scaffold Astro + TypeScript. Add Zod schemas for every collection in §4.
2. Write `methodology/v0.2.yaml` (7 dimensions × 6 levels, 9 classifications, A–D confidence) by transcribing handbook §3–§5.
3. Transcribe the **56 seed records** from §8 into watch files as `version: 1`, `is_seed: true`, `methodology_code: v0.2`. **Check every row against the PDF by hand.** The table on pp.12–14 extracts out of order, and rows had to be reconstructed by position.
4. Create organizations for every brand, plus the suppliers and groups the dataset implies (Kenissi, Sellita, Miyota, Swatch Group, Richemont, Rolex/Tudor, Seiko…).
5. Seed `sources.yaml` from §10 (22 sources), with Wayback archive links.
6. Write `scripts/validate.ts` (cross-references plus the §4.2 invariants) and run it in CI on every PR.
- **Validate:** `npm run validate` passes. A deliberately broken fixture (a sum field, a missing dimension, an unknown classification) fails.

### Phase 2: Public read-only site
1. Pages: Home, Methodology, Index (client-side filters), Watch record, Brand, About.
2. A profile strip component (U is distinct, no colour-only encoding).
3. Seed/provisional banner and confidence-D rendering (F6, F7).
4. JSON/CSV export generated at build time.
5. Deploy to static hosting with a preview deploy per PR.
- **Validate:** builds clean; Lighthouse accessibility ≥ 95; a test asserts there is no sum anywhere in the rendered output.

### Phase 3: Evidence layer (editorial-heavy)
1. Fully evidence a **pilot set of 6 records**: the handbook's showcase and edge cases (Shapiro Resurgence + Infinity, Fleming Series 1, Akmaev Koi, AWAKE vs anOrdain Model 1 Fumé, Czapek Antarctique). These exercise every rule.
2. For each: claims → provenance entries → profile v2 with per-dimension rationale and `score_evidence` → reconfirm confidence.
3. Render claims, sources, disputes, and the provenance table on the watch page.
4. Write `docs/EDITORIAL.md`: how to research, cite, archive, and write a rationale. This turns §6 into a checklist.
- **Validate:** the 6 pilot records pass invariant 4 (no seed exemption).

### Phase 4: Corrections + history + suppliers
1. Correction form → moderation queue (per Q4). Acceptance becomes a PR that references the correction id.
2. Version history and diffs between profile versions on the watch page.
3. Sources page; supplier/organization pages showing "where this supplier appears" (F14).
4. Right-of-reply process for brands (see §8).
- **Exit = MVP launch:** 56 records live (6 fully evidenced, 50 provisional), corrections working, dataset downloadable.

### Phase 5: Accounts and community editing (decided 2026-10-20)

**Updated scope:** `docs/ACCOUNTS-EDITORIAL-IMPLEMENTATION.md` supersedes this
initial short sketch, including its illustrative schema, required profile fields,
and pending-proposal visibility assumptions. The owner selected independent
FALK accounts through Replit-managed Clerk; retain exactly three app roles and
review every catalogue change. Phase 1 supplies the account/database foundation;
the contribution workflow and public revision-history UI remain later stages.

Anyone can create an account and edit any record (scores included). Every edit is reviewed by an editor before it goes live. GitHub is no longer part of contributing. See `docs/DECISIONS.md` Q12–Q14.

**Storage.** Replit's built-in PostgreSQL is the source of truth, replacing `data/` YAML. Each record, organization, and source is one JSONB document, validated by the existing Zod schemas in `src/schema.ts` and the invariants in `scripts/validate.ts`. Nothing is redesigned. The relational tables in §4.1 are not needed until a query demands them.

```sql
entity    (kind text, id text, data jsonb, current_rev bigint, PRIMARY KEY (kind, id))  -- kind: watch | organization | source
revision  (id bigserial PRIMARY KEY, kind text, entity_id text, data jsonb,              -- full document after the edit
           author text REFERENCES account, summary text NOT NULL,                     -- edit summary, as on Wikipedia
           status text CHECK (status IN ('pending','approved','rejected')),
           reviewer text REFERENCES account, review_note text, created_at timestamptz, reviewed_at timestamptz)
account   (id text PRIMARY KEY,                                                         -- illustrative provider identity; actual app uses UUID + Clerk subject
           display_name text NOT NULL,
           role text CHECK (role IN ('contributor','editor','admin')) DEFAULT 'contributor',
           background text NOT NULL,                                                     -- free text, e.g. 'watch blogger', 'hobbyist since 2010'; shown on every edit
           brand_ties text[] NOT NULL DEFAULT '{}')                                      -- organization ids the person works for; empty = none
```

Revisions are append-only, so history, diffs, and reverts all come from `revision`. The server checks roles on every write: contributors can create only `pending` revisions, and only editors can approve them.

**Flow.**
1. Sign up with an independent FALK account via managed Clerk and verify an email address. A unique public username is required; display name, bio and self-reported qualifications are optional. A real name is private by default, and a separate disclosure records organization ties. Qualifications do not grant permissions.
2. Use **Edit** on any record. This is a form for scores (0–5 or U), rationale, classification, confidence, claims, sources, and provenance. An edit summary is required.
3. On save, the document is validated with the same rules as CI. Invalid edits are refused with the specific rule that failed. Changing a score requires a rationale and a supporting claim (invariant 4).
4. The record page shows "N pending edits". Anyone can see the diff.
5. An editor approves (the document becomes current and is live on the next page load) or rejects (with a note the author can see). An editor cannot approve their own edit.
6. The author's display name and background are shown next to every edit in the review queue and in the history.
7. **Conflict of interest:** an edit to a record of a brand listed in the author's `brand_ties` is flagged in the queue and on the history page, and cannot be approved by anyone with the same tie.

**Site.** Hosted on Replit as one Node server (Astro with `@astrojs/node`, Replit Autoscale deployment). All pages are server-rendered from the database, so an approved edit is live at once with no rebuild step. Public pages send cache headers that are purged on approval. History pages and per-record talk pages replace the GitHub Discussions links.

**Steps.**
1. Set up the Replit app: add `@astrojs/node`, enable Replit PostgreSQL (`DATABASE_URL`) and independent accounts via managed Clerk, and track `.replit` again. Production domain is blocked on Q11; development uses the Replit URL.
2. Write a migration script that loads `data/` into `entity` with one approved seed revision per entity. Keep `data/` as a nightly JSON/CSV export so open data (F13) and the git trail continue.
3. Point `src/lib/data.ts` at the database at request time. The page templates don't change.
4. Accounts, the edit form, server-side validation, and pending revisions.
5. Review queue, diffs, approve/reject/revert.
6. History and talk pages; the corrections form stays for people without an account.
- **Validate:** a contributor edit with a missing rationale is refused; a pending edit is not visible on the public page until approved; a contributor cannot approve; an editor cannot approve their own edit; an edit by a brand-tied author is flagged.

**Ceiling.** Every edit is reviewed, so throughput is limited by editor time.
If the queue grows, improve review tooling and recruit editors; do not add an
automatic-publishing role or bypass review.

### After the MVP
- Evidence the remaining 50 records (ongoing editorial work).
- Git CMS for non-technical editors, then contributor accounts and community submissions.
- Methodology v0.3 (quartz/Spring Drive and in-group rules, Q7–Q8).
- A public API (the static JSON may already be enough), and i18n (FR/DE/JA are natural for this audience).

## 8. Risks

| Risk | Likelihood | Impact | Mitigation |
|---|---|---|---|
| Evidence work far outweighs dev work (56 × 7 = 392 rationales) | **High** | Launch slips | Pilot 6 records first, launch the rest as provisional, write EDITORIAL.md early |

| Classification drift returns via free text | Medium | Medium | Controlled vocabulary, CI rejects unknown codes |
| Readers treat the profile as a quality score | Medium | High | No sum, no total sort, U distinct, copy on every page |
| Seed transcription errors (the PDF table extracts out of order) | Medium | Medium | Check each of the 56 rows by hand against the PDF; a second editor reviews the PR |
| Product images and copyright | Medium | Medium | No photos in the MVP, or only with written permission |
| AI-assisted content credibility | Low–Med | Medium | Keep the transparency note; every published claim links to a human-checked source |
